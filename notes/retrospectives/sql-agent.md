## 1. 얻은 답 두 가지

랩은 *"실행 결과를 보여주면 검토가 더 잘 된다"*고 서술한다. 재현해보니 그대로였다.

```
none          0/5
text          0/5
feedback     10/10
```

여기까지는 랩을 확인한 것이다. **우리가 더 얻은 것은 그다음이다.**

### 1.1. 차이는 온도가 아니라 실행 결과다

랩의 두 검토 함수는 실행 결과 말고도 `temperature`가 다르다 — 0과 1.0. 그대로
비교하면 차이의 원인을 말할 수 없다. 그래서 **온도를 맞춘 네 번째 조건**을 넣었다.

```
feedback-t0   5/5     ← temperature 0, 실행 결과는 그대로
```

`text`(0/5)와 `feedback-t0`(5/5)는 온도가 같다. **남은 차이는 실행 결과뿐이다.**

프롬프트는 한 글자도 건드리지 않았다 — 호출 인자만 바꿨다. 재현을 깨지 않고
변인을 분리할 수 있었던 건 `temperature`를 처음부터 인자로 뺐기 때문이다.

### 1.2. 모델 비교의 상당 부분은 JSON 형식 준수였다

같은 V1, 같은 실행 결과를 네 모델에 줬다.

| 모델 | 그대로 채점 | 펜스 제거 후 |
|---|---|---|
| `gpt-4.1` | 3/3 | 3/3 |
| `gpt-4o` | **0/3** | **3/3** |
| `gpt-4.1-mini` | **0/3** | **3/3** |
| `gpt-3.5-turbo` | 0/3 | 0/3 |

`gpt-4o`의 응답을 열어보면 이렇다.

    ```json
    {
      "feedback": "...the negative sales value suggests that there might be a
                   directional issue with 'qty_delta'...",
      "refined_sql": "SELECT color, SUM(ABS(qty_delta) * unit_price) ..."
    }
    ```

**문제를 정확히 짚고 정답 SQL을 냈다.** ` ```json ` 으로 감쌌을 뿐이다.
`json.loads`가 실패했고 폴백이 원본 SQL을 유지했다.

랩은 생성된 SQL의 펜스는 `execute_sql`에서 벗기고, 검토 응답의 펜스는 벗기지 않는다.
한쪽만 처리한다. 우리는 **재현을 유지하고 대신 두 숫자를 함께 낸다**
(`rescore_without_fences()` — 저장된 원문을 다시 읽을 뿐 호출하지 않는다).

실제로 못 고친 건 `gpt-3.5-turbo` 하나인데, 그것도 *"−190571 for blue seems
incorrect"*라고 **지적은 하고 SQL은 그대로 뒀다.** 진단은 했으나 처방을 못 한 경우다.

## 2. 이 발견이 가능했던 이유

우연이 아니라 세 가지 설계 덕분이다.

| 설계 | 없었다면 |
|---|---|
| `is_json_parsed` 플래그 | 폴백은 "문제없다는 검토"와 똑같이 생겼다. 구분이 안 됐을 것 |
| 응답 원문을 `runs/`에 저장 | 재채점하려면 호출을 다시 해야 했을 것 |
| 성적표에 파싱 실패 수 표시 | `0/3`만 보고 "반성을 못 한다"로 기록했을 것 |

세 번째는 **결과를 보고 나서야 넣었다.** 처음 성적표는 `0/3`만 찍었고, 그대로
문서에 넣었으면 틀린 결론이 남았을 것이다.

> **교훈:** 실패를 세는 지표는 **실패의 종류**도 함께 세야 한다.

## 3. 프로세스에서 통한 것

### 3.1. LLM 없이 검증되는 층을 먼저 굳혔다

데이터 → 실행 → 채점기 순으로 만들고 각 층을 랩과 대조했다.

| 층 | 대조 방법 |
|---|---|
| 데이터 | 랩 생성기를 같이 돌려 **10컬럼 × 5,000행 전수 비교** |
| 실행 | 랩 `execute_sql`과 **7개 케이스** 출력 비교 |
| 프롬프트 | 노트북 f-string을 렌더해 **축자 비교** |
| 채점기 | 정답 SQL 6개 · 틀린 SQL 7종 · 표현만 다른 SQL 4종 |

덕분에 모델을 붙였을 때 **차이가 모델에서 왔다고 말할 수 있었다.** 이게 없었다면
`0/5`를 보고 우리 버그를 의심하는 데 시간을 썼을 것이다.

### 3.2. 검사가 잘못된 가정을 잡아냈다

`ts`의 distinct 값이 **정확히 1개**라고 불변식에 박았는데 실행하니 2개가 나와 실패했다.
`CURRENT_TIMESTAMP`가 1초 해상도라 삽입이 초 경계를 넘으면 갈린다. **한 번 관측한
결과를 성질로 착각한 것**이다. 개수가 아니라 **폭**으로 검사하도록 고쳤다.

### 3.3. 반례로 검사를 검사했다

통과만 하는 검사는 쓸모없어서, 일부러 깨뜨려 확인했다.

- 시드·비율·제품 수 변경 → 불변식이 잡음
- `notes` 한 줄 변경 → **값 불변식은 통과**, 행 대조가 잡음 (두 검사가 다 필요한 이유)
- en-dash · 공백 하나 · 앞 개행 → 프롬프트 검사가 잡음
- `SELECT 'interrupted'` → 타임아웃 오탐 없음

## 4. 구현하며 걸린 것

### 4.1. 공개 이름이 기획서와 갈라졌다 — 세 번

`execute_sql`→`run_query`, `review_sql`→`refine_sql`, `--reflection`→`--condition`.

매번 코드가 먼저 나오고 문서가 뒤따라 맞춰졌다. **문서가 조용히 코드를 따라가면 기획은
검증 기준이 아니라 사후 기록이 된다.** [체크리스트 규칙 7](../../projects/sql-agent/CHECKLIST.md)로
넣었다.

### 4.2. 검증하지 않은 평가 질문이 들어갔다 — 두 번

| 질문 | 문제 |
|---|---|
| *"2025년 5월에 몇 개 팔렸나?"* | `ts`에 변동이 없어 **0행** |
| *"total value of inventory added?"* | `restock`의 `unit_price`가 전부 NULL이라 **NULL** |

첫 번째는 문서에 들어간 뒤 발견됐고, 두 번째는 그 교훈으로 넣기 전에 걸렀다.
지금은 여섯 질문 모두 `EXPECTATIONS`에 정답과 함께 있고 실행으로 확인된다.

### 4.3. 비결정적 결과가 완료 기준에 들어갔다

초안의 대표 지표는 *"3.2.1은 실패하고 3.2.2는 성공한다"*였다.
`refine_sql_external_feedback`이 `temperature=1.0`이라는 것이 **같은 문서에 ⚠로
적혀 있는데도** 그랬다. 성공률로 바꿨다.

> [chart-agent 회고](chart-agent-lab-findings.md)에 *"같은 입력에도 비평이 달라진다"*를
> 이미 적어뒀었다. **회고는 쓰는 것으로 끝나지 않고 다음 기획에서 꺼내 봐야 한다.**

### 4.4. `sqlite3`의 `with`는 연결을 닫지 않는다

```python
with sqlite3.connect(path) as conn:   # 트랜잭션만 커밋, 연결은 열린 채
```

임시 디렉터리 안의 DB를 연 채로 블록을 나가는 코드가 있었다.
`contextlib.closing`으로 통일했다.

## 5. 공통 모듈 추출 판단

체크리스트가 미뤄둔 항목이다. **이제 사례가 2개이므로 실제로 재봤다.**

| 모듈 | chart | sql | 공통 | 판단 |
|---|---:|---:|---:|---|
| `trace.py` | 64 | 68 | **72%** | 추출 가치 있음 |
| `config.py` | 130 | 145 | **61%** | 추출 가치 있음 |
| `llm.py` | 136 | 75 | 41% | 일부만 |
| `report.py` | 92 | 134 | 20% | 사실상 다름 |

`llm.py`가 41%인 것은 chart 쪽에만 이미지 경로가 있기 때문이고, `report.py`가
20%인 것은 보여줄 것이 다르기 때문이다(차트 vs SQL 표). **둘은 애초에 공통이 아니었다.**

진짜 공통은 **`config`의 키 검증·provider 판별**과 **`trace`의 타이밍 기록**이다.
합쳐야 100줄 남짓이다.

**지금은 추출하지 않는다.** 근거:

- 공유 패키지를 만들면 두 프로젝트가 그것을 임포트해야 하는데, 이 워크스페이스는
  패키징이 없어 경로 조작이 붙는다. 100줄을 아끼려고 그 마찰을 들이는 건 손해다
- 모듈 3 이후 프로젝트가 더 생긴다. **세 번째 사례가 나올 때가 적기다**

대신 **무엇이 공통인지는 여기 적어둔다** — 그때 다시 재지 않아도 되도록.

```
config: _check_repo_root · _provider_of · load_environment · is_anthropic
        require_key · REQUIRED_KEY_BY_PROVIDER · PROVIDER_SEPARATOR
trace:  StepRecord · RunTrace.timed · RunTrace.save
```
