# 02. 왜 직접 생성으로는 부족한가 (Why not just direct generation?)

> Module 2 · Lesson 2
> 이전 ← [01. 리플렉션으로 결과물 개선하기](01-reflection-basics.md) · 다음 → [03. 차트 생성 워크플로우](03-chart-generation-workflow.md)

## 한 줄 요약

직접 생성(제로샷)은 한 번에 끝내는 방식이다.
연구 결과 리플렉션을 적용하면 **같은 모델로도 일관되게 더 높은 성능**이 나온다.

---

## 1. 직접 생성 vs. 리플렉션

**직접 생성(direct generation):** LLM에게 한 번 프롬프트하고 그 출력을 그대로 사용

```
"블랙홀에 관한 에세이를 써줘"        → 출력 그대로 사용
"복리 계산 파이썬 코드를 작성해줘"    → 출력 그대로 사용
```

이를 **제로샷 프롬프팅(zero-shot prompting)** 이라고도 합니다. 프롬프트에 원하는 출력의 예시가 **전혀 포함되지 않았다**는 뜻입니다.

## 2. 용어 — 제로샷 / 원샷 / 퓨샷

| 용어 | 프롬프트에 포함된 예시 수 |
|---|---|
| **제로샷 (Zero-shot)** | 0개 |
| **원샷 (One-shot)** | 1개 (입력-출력 쌍) |
| **퓨샷/투샷 (Few-shot)** | 여러 개 |

> 이 구분은 배경 지식일 뿐 이번 레슨의 핵심은 아닙니다.
> "제로샷 = 예시 없이 한 번에" 정도로 기억하면 충분합니다.

## 3. 연구 근거

Madaan 등의 논문에서 인용된 비교입니다.

- **밝은색 막대**: 제로샷 프롬프팅
- **어두운색 막대**: 동일 모델 + 리플렉션

여러 작업과 모델(GPT-3.5, GPT-4 등)에 걸쳐, **리플렉션을 적용한 쪽이 일관되게 더 높은 성능**을 보였습니다.

⚠ 다만 결과는 **구체적인 애플리케이션에 따라 달라집니다.** 내 작업에서 얼마나 효과가 있는지는 직접 재봐야 합니다 — [05번 노트](05-evaluating-reflection.md)의 주제입니다.

## 4. 리플렉션이 도움이 되는 실제 사례

| 작업 | 리플렉션이 잡아내는 것 |
|---|---|
| **구조화된 데이터 생성**<br>(HTML 테이블, 깊게 중첩된 JSON) | 형식 오류. 복잡한 구조일수록 효과가 큼 |
| **순차적 지시사항**<br>(차 우리는 단계 등) | 누락되거나 앞뒤가 안 맞는 단계 |
| **도메인 이름 브레인스토밍**<br>(강사가 AI Fund에서 실제로 한 작업) | 발음이 어려운 이름, 다른 언어에서의 부정적 의미 |

⚠ 아주 기본적인 HTML처럼 **LLM이 이미 잘하는 작업에는 효과가 크지 않습니다.** 리플렉션은 어려운 작업일수록 값을 합니다.

## 5. 검토 프롬프트 예시

**도메인 이름:**
```
제안된 이름 검토
  → 발음하기 쉬운가 확인
  → 여러 언어에서 부정적 함의가 있는가 확인
  → 두 기준을 모두 통과한 이름만 출력
```

**이메일 초안:**
```
첫 초안 검토
  → 어조(tone) 확인
  → 언급된 사실과 약속이 정확한가 검증
  → 발견된 문제를 바탕으로 수정본 작성
```

## 6. 좋은 검토 프롬프트를 쓰는 법

1. **검토하라고 명확히 지시할 것**
2. **평가 기준을 구체적으로 명시할 것** — "발음 용이성 확인", "어조 확인", "사실 검증"
   → LLM이 무엇을 중요하게 볼지 방향이 잡힘
3. **남의 프롬프트를 많이 읽을 것** — 잘 설계된 오픈소스 프로젝트의 프롬프트가 좋은 교재

> 2번이 실전에서 가장 큰 차이를 만듭니다.
> "검토해줘"만 쓰면 모호한 칭찬이 돌아오고, 기준을 주면 구체적 지적이 돌아옵니다.
